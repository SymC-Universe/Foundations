# Stability Arc Continuity and Failure-Signal Protocol v0.1

Status: ACTIVE project-control protocol
Scope: Stability Arc / Generator-First Stability Architecture investigation

## 1. Canonical continuity rule

No scientifically material artifact may remain chat-only if it is needed for later execution, audit, derivation, or interpretation.

The canonical durable home for the active investigation is the GitHub repository `SymC-Universe/Foundations`, with the current working branch named explicitly in the live state file. Chat transcripts, project summaries, temporary runtimes, and local session files are supporting context only, not canonical storage.

Every new material artifact should be persisted to the repository as soon as it is mechanically safe to do so, including:

- preregistrations and amendments;
- code and exact configuration;
- input manifests and hashes;
- raw or minimally transformed numerical outputs when size permits;
- closure audits and failure analyses;
- reproducibility guides;
- interpretation firewalls and non-claims;
- current-state / next-step records;
- provenance links to oversized external artifacts.

If an artifact cannot be committed directly because of size, format, or access constraints, a repository pointer record must identify its exact durable location, SHA-256 when available, creation/source lineage, and how to recover it.

A document being generated by ChatGPT is not evidence that it will remain byte-accessible in later chats. Persistence is established only when the artifact has been written to a durable store such as GitHub or another explicitly recorded canonical archive.

## 2. Live-state requirement

Maintain a compact machine- and human-readable project state that records:

- current canonical branch and head commit;
- latest closed scientific phase;
- active phase;
- next executable step;
- active external runs and run IDs;
- unresolved blockers and classifications;
- required user actions, if any;
- frozen scientific contracts governing the next run;
- hashes/paths of the authoritative preregistration and execution code.

The live-state record must be updated at every meaningful checkpoint so a future thread does not need to reconstruct the investigation from conversation memory.

## 3. Failure is evidence, not trash

Every failed, held, nonidentifiable, divergent, null, or mechanically aborted result must be preserved and investigated before the branch is considered understood.

A failure analysis must first classify the event without changing scientific settings:

1. MECHANICAL: infrastructure, dependency, permission, memory, timeout, serialization, runner, malformed artifact, or execution defect.
2. PROVENANCE: hash mismatch, missing source, inconsistent metadata, ambiguous input identity, or broken lineage.
3. NUMERICAL: convergence, precision, discretization, conditioning, finite-size, solver instability, or reproducibility defect that prevents scientific interpretation.
4. IDENTIFIABILITY: the permitted observables do not support the requested inference under the frozen protocol.
5. MODEL-BOUNDARY: the model/approximation is internally valid but ceases to represent the tested regime or observable adequately.
6. SCIENTIFIC: the preregistered prediction or relationship fails under an otherwise admissible test.

Mixed failures may receive more than one label, but the evidence for each label must be explicit.

## 4. Required failure investigation

Before a failure is closed, record as applicable:

- exact failed gate or hypothesis;
- exact inputs, code/version, environment, hashes, and raw output/log lineage;
- last known valid checkpoint;
- reproducibility of the failure where a repeat is scientifically and computationally admissible;
- whether neighboring cases, controls, residuals, spectra, or diagnostics reveal a boundary rather than random error;
- what parameter region, model class, inference, or mechanism the failure excludes or constrains;
- whether the failure exposes a previously unrecognized confound, degeneracy, hidden coordinate, identifiability limit, or competing explanation;
- what evidence would distinguish the plausible explanations;
- whether a new prospective hypothesis is justified.

Do not repeat a known mechanical failure on the same inadequate resource merely to reproduce it. Preserve enough evidence to diagnose it, then change only the demonstrated mechanical condition.

## 5. Scientific failure lineage

A scientific failure must remain visible in the evidence ledger permanently.

It may generate a narrower or different hypothesis, but:

- the original claim remains failed under its original registration;
- the new hypothesis must be labeled post-hoc at birth;
- the new hypothesis must receive a new preregistration/version;
- evidence used to formulate the new hypothesis cannot be counted as prospective confirmation of that hypothesis;
- promotion requires genuinely fresh evidence or an untouched holdout that was protected before the hypothesis was formed.

Failure-derived hypotheses are scientifically valuable precisely because the failure remains part of their lineage.

## 6. Anti-circularity interaction

This protocol operates together with `stability_arc/gfsa_v0.7.2/ANTI_CIRCULARITY_GUARD_v0.1.md`.

Failure investigation may inspect failed outcomes deeply to understand them, but it may not retroactively alter the registered scoring rule and then reclassify the same evidence as a prospective success.

Exploratory analysis after a failure is allowed and encouraged when clearly labeled exploratory. Any rule learned from that analysis must be frozen before it is tested prospectively.

## 7. Continuity controller behavior

The automated continuity controller should:

- advance safe mechanical/provenance/reproducibility work without waiting for user approval;
- preserve and investigate failures rather than merely marking them failed;
- maintain the live-state record;
- ensure newly generated material artifacts are persisted or explicitly indexed;
- stop before changing frozen science, preregistered rules, or conclusions;
- report exact user action only when a required action cannot be performed through available repository/tool access.

## 8. Closure condition

A failed branch is not closed merely because execution stopped. It is closed only when the failure is classified, its evidence is preserved, its scientific or mechanical signal is understood to the extent supported by available evidence, and the next justified action is recorded as one of:

- mechanical repair and exact rerun;
- independent numerical/reproducibility audit;
- identifiability/nonidentifiability closure;
- model-boundary closure;
- new preregistered prospective test;
- scientific rejection with no justified continuation.
